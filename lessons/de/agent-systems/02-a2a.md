# A2A: Agenten, die an Agenten delegieren

Agentensysteme und Standards · Kapitel 2 von 8 · 25 Minuten

Wie ein Agent einen anderen über dessen Agent Card findet und ihm einen Task übergibt, den er bis zum Ende verfolgen kann.

## Ziele

- Lies die Agent Card des Payments-Agenten.
- Verfolge einen Task von WORKING über INPUT\_REQUIRED bis COMPLETED.
- Antworte auf eine Task-ID, die nicht dir gehört, und sieh, wie sie abgelehnt wird.
- Bring den Austausch in die richtige Reihenfolge.

## Der Text

### Ein Gegenüber, kein Tool

A2A (Agent2Agent, Protokoll 1.0) verbindet Agenten, die verschiedene Parteien betreiben. Im vorigen Kapitel hat der Support-Agent Tools auf einem MCP-Server aufgerufen: Funktionen mit einem Schema, die genau so laufen, wie sie aufgerufen werden. Über A2A übergibt er Arbeit an einen anderen Agenten, der mit seinem eigenen Modell, seinen Tools und seinem Gedächtnis entscheidet, wie er sie erledigt. Der Aufrufer sieht nur den Task und seine Ergebnisse.

### Die Agent Card

Jeder A2A-Server hat eine Agent Card. Ein öffentlicher Agent stellt sie unter /.well-known/agent-card.json bereit, wo jeder sie ohne Zugangsdaten lesen kann. Sie nennt den Agenten und seine Skills, listet seine Schnittstellen (URL, Binding wie JSONRPC, Protokollversion), sagt, ob er streamen kann, und legt fest, wie man sich authentifiziert, hier mit einem Bearer-Token pro Händler. Jede Anfrage trägt einen A2A-Version-Header; ein Server lehnt eine Version ab, die seine Card nicht listet (Fehler -32009).

### Nachrichten, Tasks und Artefakte

Der Client ruft SendMessage mit einer Nachricht aus Teilen auf: Text für das Modell des anderen Agenten und Datenteile mit einem Medientyp für Werte, auf die er sich verlassen kann, etwa die Bestell-ID und den Betrag. Die Antwort ist eine Nachricht oder, bei Arbeit, die Zeit braucht, ein Task: eine ID, eine contextId, die eine Unterhaltung zusammenfasst, und ein Status wie TASK\_STATE\_WORKING, INPUT\_REQUIRED oder COMPLETED. Ergebnisse kommen als Artefakte am Task an, getrennt vom Chat.

INPUT\_REQUIRED pausiert den Task, bis der Client antwortet. Die Antwort ist eine neue Nachricht, die dieselbe taskId und contextId nennt. Der Server hält die Tasks jedes Händlers getrennt: Eine Antwort, die einen Task nennt, der nicht diesem Händler gehört, bekommt -32001, task not found, und nichts läuft.

### Streaming oder Polling

Mit SendStreamingMessage schickt der Server Server-Sent Events: zuerst den Task, dann Status- und Artefakt-Updates, bis der Task pausiert oder endet. Ohne Streaming antwortet SendMessage, wenn der Task pausiert oder endet; mit returnImmediately antwortet es sofort, und der Client fragt GetTask per Polling ab.

### Was du hier tust

Haldens Support-Agent und der Payments-Agent nutzen beide das offizielle A2A JavaScript SDK (@a2a-js/sdk 1.3.0) auf dieser Seite, jeder gesteuert von einem geskripteten LangChain-Modell. Lies die Card, verfolge den Erstattungs-Task durch seine Status und beantworte seine Frage selbst. Schalte dann Abfangen ein und richte deine Antwort auf den Task eines anderen Händlers. Ein optionaler Schritt zeigt, wie der Payments-Agent sein Ledger über MCP erreicht, wobei aus MCPs input\_required das INPUT\_REQUIRED des A2A-Tasks wird.

## Check

Bring den A2A-Austausch für die Erstattung in die richtige Reihenfolge.

1. GET der Agent Card.
2. SendMessage mit der Erstattungsanfrage.
3. Task in TASK\_STATE\_WORKING.
4. Task in TASK\_STATE\_INPUT\_REQUIRED.
5. SendMessage mit der Antwort, am selben Task.
6. Task in TASK\_STATE\_COMPLETED, mit dem Erstattungsbeleg als Artefakt.

**Warum:** Zuerst kommt die Discovery, dann durchläuft der Task seine Status. Die Antwort nennt die ID des Tasks, also findet der Server den pausierten Task und setzt ihn fort. Eine Antwort, die den Task eines anderen Händlers nennt, findet nichts und bekommt -32001.

## Was du jetzt kannst

- Eine Agent Card lesen und einen Skill und eine Schnittstelle wählen.
- Eine Nachricht senden und die Status eines Tasks bis zu seinen Artefakten verfolgen, per Stream oder per Polling.
- Einen Task in INPUT\_REQUIRED mit einer Antwort auf dieselbe taskId und contextId beantworten.
- Erklären, wann A2A statt MCP passt.
