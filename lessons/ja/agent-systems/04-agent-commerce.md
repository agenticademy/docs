# 支払うエージェント：UCPとAP2

エージェントシステムと標準 · 第4章（全8章） · 25分

エージェントがUCPで加盟店のチェックアウトを進める方法と、AP2のマンデートが支払いを人の署名した内容に結びつける方法。

## 目標

- チェックアウトセッションを作成して完了します。
- スマートフォンでマンデートに署名します。
- 署名の後で金額を変え、検証が失敗するのを確かめます。
- 確認問題に合格します。

## 本文

### UCP：チェックアウト

UCP（Universal Commerce Protocol、バージョン2026-08-25）は、ショッピングエージェント（プラットフォーム）が加盟店（ビジネス）から購入するための仕組みです。ビジネスは/.well-known/ucpにプロファイルを公開します。バージョン、checkoutなどの機能、決済ハンドラー、RESTエンドポイントです。エージェントはそれを読み、POST /checkout-sessionsでチェックアウトセッションを作成し、ステータスがready\_for\_completeになるまでPUTで更新し、POST …/completeで終えます。

すべての呼び出しはプラットフォーム自身のプロファイルを指すUCP-Agentヘッダーを持つので、ビジネスはプラットフォームが何に対応しているかを確認できます。すべての書き込みはIdempotency-Keyを持ちます。タイムアウトでエージェントが同じリクエストを再送しても、ビジネスは2回処理せずに最初の結果を返します。Haldenの注文48213のような二重請求こそ、これが防ぐものです。

### AP2：人の署名

UCPだけでは、セッションを持つ者を誰でも信頼します。AP2（Agent Payments Protocol）は同意の証明を加えます。エージェントのプロバイダーは、SD-JWTの検証可能な資格情報として2つのマンデートを発行します。Haldenが署名したチェックアウトそのもののハッシュを持つチェックアウトマンデートと、金額、受取人、カードを持つ支払いマンデートです。人はエージェントが描画できない画面、つまりスマートフォンのウォレットでそれを確認し、スマートフォンの鍵がそれぞれにキーバインディングJWTの署名をします。

Haldenは、チェックアウトマンデートを自分が署名したチェックアウトと照合します。カードウォレットは、その金額の決済トークンを発行する前に支払いマンデートを確認し、決済処理業者は請求する前にトークンを確認します。人が署名した後でカートや金額を変えると、エージェントが何を言おうと、ハッシュや署名が一致しなくなります。

ここでは人がその場にいます。AP2の自律モードでは、人はその場にいません。最高価格などの上限を付けたオープンなマンデートを前もって承認し、エージェントはその範囲内で最終的なマンデートに署名します。

### ANPを2文で

ANP（Agent Network Protocol）は、オープンなWebで出会うエージェントのためのものです。各エージェントはdid:wba識別子を持ち、そのDIDドキュメントは自分のドメインから配信され、公開鍵を並べます。すべてのリクエストはHTTP Message Signaturesで署名されるので、相手はアカウントなしにどのエージェントが送ったかを知ります。「さらに先へ」のステップにあるANPのラボでこれが動きます。

### ここですること

ショッピングエージェントがHaldenのテントRidge 2を購入します。チェックアウトを追い、スマートフォンで承認し、次に「傍受」をオンにしてもう一度実行し、署名の後で金額を上げます。

## 確認問題

### 質問1/4

AP2のチェックアウトマンデートは何を固定しますか。

- エージェントの名前。
- **✓** 人が承認した、カートと合計を含むチェックアウトそのもののハッシュ。
- 加盟店のロゴ。

**理由:** マンデートは、人が何を買うことに同意したかの署名付きの証明です。異なるチェックアウトはハッシュも異なるので、一致しなくなります。

### 質問2/4

人が署名した後で、エージェントが金額を上げます。どこで失敗しますか。

- エージェントが理由を説明すれば、どこでも失敗しない。
- **✓** 検証で。カードウォレット、Halden、決済処理業者のどれかが、署名かハッシュが一致しないことに気づく。
- 数日後、銀行でだけ。

**理由:** 各当事者は、目の前の値と署名を照合します。エージェントが言葉でハッシュを通り抜けることはできません。

### 質問3/4

UCPのIdempotency-Keyは何を防ぎますか。

- プロンプトインジェクション。
- **✓** 再試行したリクエストが2つ目の注文や請求を作ること。
- 期限切れのカード。

**理由:** ネットワークの再試行はリクエストを繰り返します。同じキーなら、ビジネスは2回処理せずに最初の結果を返します。Haldenの話の二重請求こそ、これが防ぐものです。

### 質問4/4

人がエージェントのチャットではなく、スマートフォンのウォレットで承認するのはなぜですか。

- スマートフォンの画面のほうが大きいから。
- **✓** エージェントはウォレットの画面に描画できず、マンデートに署名する鍵はスマートフォンだけが持っているから。
- UCPがスマートフォンを必要とするから。

**理由:** AP2はこれを信頼できるサーフェスと呼びます。人は発行されたとおりのマンデートを見て、署名はエージェントが決して持たない鍵から来ます。

## これでできること

- UCPのチェックアウトセッションを、プロファイルからcompletedまで追えます。
- AP2のマンデートが、支払いを人の署名付きの同意にどう結びつけるかを説明できます。
- べき等キーを使って、再試行を安全にできます。
- ANPのdid:wbaと署名付きリクエストが加えるものを2文で説明できます。
