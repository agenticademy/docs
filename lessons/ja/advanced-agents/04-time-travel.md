# タイムトラベル

高度なエージェント · 第4章（全10章） · 20分

スーパーステップごとにチェックポイントが保存されるので、実行の履歴を読み、過去のステップからリプレイし、過去の状態を編集して、2つ目の結末をフォークできます。

## 目標

- 5ノードのグラフをスレッド上で実行し、チェックポイントの履歴を読む。
- ステップ3まで巻き戻し、そこからリプレイする。
- ステップ3の状態を編集してフォークし、2つの結末を比べる。
- フォークの手順を正しい順番に並べる。

## 本文

### スレッドはタイムライン

グラフをチェックポインター付きでコンパイルし、thread\_idを付けて実行すると、エージェントシステムのパスで見たように、LangGraphはスーパーステップごとに状態全体のチェックポイントを保存します。各チェックポイントには、固有のcheckpoint\_id、メタデータ内のstepとsource（step -1が入力）、そして1つ前のチェックポイントを指すparentConfigがあります。親でつながったスレッドのチェックポイントはタイムラインになり、タイムラインは枝分かれできます。

### 過去を読む

getStateHistory({ configurable: { thread\_id } })は、スレッドのすべてのチェックポイントを新しい順に並べます。各項目は状態のスナップショットで、values、next（次に実行するノード）、config、metadataを持ちます。configにcheckpoint\_idを入れたgetStateは、そのうちの1つを読みます。これが巻き戻しです。過去の状態を見るだけで、何も変えません。

### リプレイとフォーク

過去のチェックポイントを指すconfigでinvoke(null, config)を呼ぶと、そこからリプレイします。そのチェックポイントより前のノードは再実行されず、後のノードは再実行されるので、本物のモデルなら2回目は違う答えを返すかもしれません。新しいチェックポイントは新しいブランチに積まれ、そのブランチはsourceがforkのコピーから始まります。古いチェックポイントは残ります。

updateState(config, values, asNode)は、過去を消さずに変えます。configが指すチェックポイントの上に、sourceがupdateの新しいチェックポイントを、ノードasNodeがvaluesを返したかのように書き込み、新しいチェックポイントのconfigを返します。invoke(null, thatConfig)を実行するとスレッドがフォークします。最初の結末は履歴に残り、2つ目の結末があなたの編集から伸びます。checkpoint\_idなしのgetStateは最新のチェックポイントを読み、それは今ではフォークの終わりです。

### durability

実行のdurabilityオプションは、チェックポイントをいつ書き込むかを決めます。デフォルトの"async"は次のスーパーステップの実行中に各チェックポイントを保存し、"sync"は次のスーパーステップが始まる前に保存し、"exit"は実行の終了時にだけ保存します。"exit"は書き込みが最も少ないものの、巻き戻せる過去のステップが残らず、プロセスが途中でクラッシュしたときに再開する場所もありません。

### ラボ

チケットT-48213に対するHaldenの返金チェックは、read\_ticket、classify、list\_charges、decide、draft\_replyの5つのノードを順に実行します。このページでLangGraph.js 1.5.1とそのMemorySaverが動き、classify、decide、draft\_replyは台本どおりに答えるモデルに問い合わせます。ブラウザー版のLangGraph.jsにはAsyncLocalStorageがないので、各ノードは自分のconfigを明示的にモデルへ渡します。

## 確認問題

過去のチェックポイントから実行をフォークする手順を、正しい順番に並べてください。

1. チェックポインターとthread\_idを付けてグラフを実行する。
2. getStateHistoryでスレッドのチェックポイントを一覧にする。
3. 戻りたいチェックポイントをcheckpoint\_idで選ぶ。
4. そのチェックポイントのconfigと新しい値でupdateStateを呼ぶ。
5. updateStateが返したconfigでinvoke(null, config)を呼ぶ。
6. フォークの結末を、履歴に残っている最初の結末と比べる。

**理由:** チェックポイントは、スレッド上の実行が保存して初めて存在し、過去のものはgetStateHistoryの中からcheckpoint\_idで見つけます。updateStateにはそのチェックポイントのconfigが必要で、書き込んだ新しいチェックポイントのconfigを返します。そのconfigでinvoke(null, …)を呼ぶとフォークが実行されます。何も上書きされないので、最初の結末は比べるために残っています。

## これでできること

- getStateHistoryでスレッドのチェックポイントを読み、getStateとcheckpoint\_idでそのうちの1つを読む。
- 過去のチェックポイントから実行をリプレイし、どのノードが再実行されるかを説明する。
- updateStateで過去の状態を編集し、スレッドをフォークして、2つの結末を比べる。
- 各モードで巻き戻せる先がどう残るかを知ったうえで、durabilityモードを選ぶ。
